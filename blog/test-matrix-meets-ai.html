When the test matrix has to cover the model

  • May 2026
  • By An Li

For most of my career the test matrix has been a stable thing. You map the product's critical paths, the platforms you support, and the risks the business actually cares about, then build coverage outward from there. The strategy follows the product, and the product follows the business. That has been the job, and for years its shape barely moved.

It is moving now.

As companies put real budget and roadmap behind AI, the test strategy has to move with them. It is not only that there are new features to cover. The definition of quality is picking up a dimension that most QA orgs do not yet have a column for: the quality of what the model produces. Text, images, audio, video, and increasingly something inside a specific professional domain, like a legal summary or a clinical note. For years, judging whether that output was any good belonged to the AI/ML scientists who built the model. QA owned user flows, stability, performance, and security. If you lead QA today, that split is getting harder to defend, because the thing the business is selling is now the output itself.

So how do you actually test it? I find it useful to split the problem into two kinds of failure.

The failures you already know about

The first kind is the regression you can describe in advance. You know what good looks like for a given input, and you want to catch the day the model stops producing it. The standard answer here is solid and worth adopting now: build a golden dataset of inputs with reference answers, run the model, and compare. Where the output is open-ended and an exact-match check makes no sense, a second model grades it, the pattern people call LLM-as-a-judge. Evidently AI has a clear walkthrough of both (linked at the end).

This works, with one honest caveat. The judge is itself a model, and it has biases. It tends to prefer longer answers, it can favor whatever sits first in a pairwise comparison, and it will sometimes rate its own family of models too kindly. You manage that with chain-of-thought prompts, a few anchored examples, and by tuning the judge against real graded data instead of trusting it out of the box. Treat the judge as a test that also needs testing.

Golden datasets give you a baseline and a regression alarm. What they cannot do is find the failure you never thought to write down.

The failures you haven't imagined yet

This is the open problem, and it is where the interesting work is happening. Two directions are worth watching, and they are complementary rather than competing.

The first is metamorphic testing, and I think it is the most underused idea in this whole space. Instead of asserting an exact output, you assert a relation between inputs and outputs. Rephrase a question and the classification should not change. Add an irrelevant sentence and the answer should stay the same. Translate the input and the sentiment should survive. You are not saying what the right answer is, only how the output should behave when you perturb the input in a known way. That sidesteps the hardest part of testing a generative system, which is that there is no single correct answer to compare against. Frameworks like METAL can generate these relations from templates by the hundred. It is also the most QA-native technique on this list, because defining good metamorphic relations is exactly the kind of edge-case thinking testers are already good at.

The second direction is the one I want to be careful about, because it is easy to oversell. The idea is to build an adversarial model whose job is to attack the model under test, hunt for the prompts and edge cases that make it fail, and keep the ones that work so it gets sharper over time. This is real. Systems like AutoRedTeamer do exactly this, accumulating an attack library across runs in what the authors call lifelong attack integration. My honest read, though, is that today this line of work lives almost entirely in safety and security: jailbreaks, harmful or biased output, prompt injection. It is very good at finding ways to break a model. It is not yet a way to certify that a model is correct. So I would put it on the roadmap as a direction worth betting on, not as the settled future of output quality. If an earlier version of this argument read more like red teaming than QA, that was the tell, and the distinction matters.

Offline evaluation is not enough

One more thing the matrix has to absorb. Everything above is offline evaluation, run before release. Models drift, inputs drift, and users do things your dataset never imagined. So the same teams are adding a runtime layer: guardrails that check inputs and outputs live for things like leaked PII, toxic content, or malformed format, and observability that watches production signals such as refusal rate, latency, and answer drift. Offline evals tell you the model was good last Tuesday. The runtime layer tells you whether it is still good right now.

What this means if you run QA

None of this throws out the matrix we already have. User flows still break, systems still fall over, and security matters more now, not less. What changes is that a new set of rows shows up: known-regression evals, metamorphic relations, adversarial probing, and live guardrails. I don't think anyone has the finished playbook yet, and I am wary of anyone who says they do.

The QA leaders who start learning how model output gets evaluated now, rather than handing it to the model team and looking away, are the ones who will still own the word "quality" when quality means more than a green user flow.
