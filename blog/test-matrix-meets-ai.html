When the test matrix has to cover the model

  • May 2026
  • By An Li

For most of my career the test matrix has been a stable thing. You map the product's critical paths, the platforms you support, and the risks the business actually cares about, then build coverage outward from there. The strategy follows the product, and the product follows the business. That is the job, and for years the shape of it barely moved.

It is moving now.

As companies put real budget and roadmap behind AI, the test strategy has to move with them. It is not only that there are new features to cover. The definition of quality is picking up a dimension that most QA orgs do not yet have a column for.

That dimension is the quality of what the model produces.

A new column nobody owns yet

Look at what a model actually outputs: text, images, video, audio, and increasingly something inside a specific professional domain, like a legal summary or a clinical note or a financial classification. For years, judging whether that output was any good belonged to the AI/ML scientists and the engineers who built the model. They ran their own evaluation. QA, meanwhile, owned user flows, system stability, performance, and security. Two tracks that rarely crossed.

Those QA tracks are not going anywhere. User flows still break. Systems still fall over under load. Security probably matters more now, not less. But if you run QA, whether your title is QA Manager or QA Lead or CQO, there is an uncomfortable question waiting: can you keep treating model output as someone else's evaluation problem? I don't think we can for much longer. The thing the business is now selling is the output. If QA has no opinion on its quality, QA is testing the wrapper and ignoring the product.

Where to start: prompts and golden datasets

So what does testing a model actually look like? A reasonable place to start is prompt testing, which got a lot more concrete over 2025. The pattern that has held up is regression testing against a golden dataset. You curate a set of inputs with known-good reference answers, run the model, and compare. Evidently AI has a clear walkthrough of this for LLMs (linked at the end).

If you have ever written assertions it will feel familiar, with one catch: the comparison is usually a similarity judgment rather than an exact match, and that catch is where most of the real work hides. Deciding what "close enough" means for your domain is the hard part, and it is a QA decision, not a model decision.

Where it goes next: adversarial verification

Golden datasets give you a baseline. They tell you when something regressed against cases you already thought of. What they do not do is find the failure you never wrote down.

That is where I think this goes next, and it borrows from adversarial modeling. Instead of only checking against a fixed reference set, you build a second model whose whole job is to attack the output of the model under test. It hunts for the prompts, the edge cases, and the domain traps that make the first model fail. Run that loop long enough in a narrow domain and the attacker gets sharper. You end up with a verification model that understands your domain a little better every week, and that improves the more you use it. A test asset that compounds instead of decaying is rare, and worth building toward.

None of this throws out the matrix we already have. It adds a row. The QA leaders who start learning how model output gets evaluated now, rather than handing it off, are the ones who will still own the word "quality" when quality means more than a green user flow.
